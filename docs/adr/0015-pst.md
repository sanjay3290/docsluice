# 0015. Outlook PST: detect only; a reader belongs in a separate plugin

- Status: Accepted
- Date: 2026-10-10
- Requirement IDs: PRD section 8.1 (Email, P2), EXT-4, SEC-12, RT-2

## Context

Issue #87 asks for MBOX messages as children, and for an assessment of PST before any PST code is written. [MS-PST] is public. It defines three layers:

1. **The node database (NDB).** A header, then two B-trees: nodes and blocks. Data blocks may be "encrypted" with a permutation or a cyclic cipher. XBLOCK and XXBLOCK trees span data larger than one block, and subnode B-trees hang off nodes. The format has ANSI (32-bit) and Unicode (64-bit) variants, and a 4K-page variant from Outlook 2013.
2. **The lists, tables and properties layer (LTP).** Heap-on-node, B-tree-on-heap, property contexts and table contexts, with variable-size property storage.
3. **The messaging layer.** Folders, the hierarchy, contents and associated-contents tables, messages, recipients and attachment tables, and named-property maps.

Facts that shape the decision:

- PST files are routinely gigabytes. Reading one well needs random access to the file, not one `Uint8Array` in memory. The core API takes bytes or a stream and reads under `inputBytes` (100 MB by default).
- A useful reader is several thousand lines across the three layers, with its own fuzzing surface.
- A PST holds a whole mailbox: personal data at a scale that a caller should choose explicitly.
- No licence problem: [MS-PST] is under Microsoft's Open Specifications Promise, and a clean-room implementation is possible.

## Decision

docsluice does not read PST in this release.

- The core detection recognizes the PST signature (`!BDN`) as the format `pst`. Such a file fails with `UNSUPPORTED_FORMAT` instead of being treated as unknown bytes.
- A PST reader, if it is built, ships as a separate opt-in format plugin through the plugin API (EXT-4), like the opt-in 7z and RAR listers (issue #86). It would take a random-access source and give one child per message (EML-like documents) under the shared budget.
- Building it needs its own issue: scope, a corpus made without real mailboxes, and a size budget.

MBOX, a plain-text format, is a core reader (`docsluice/mbox`).

## Consequences

- No PST code or dependency now. The core stays small and runtime-neutral.
- Callers get a clear `UNSUPPORTED_FORMAT` for `.pst` files. Outlook `.msg` files (one message each) remain supported.
- A future PST plugin must first solve random access over a source larger than memory. It must also count every B-tree page, heap and property against the budget, and survive cyclic B-trees (SEC-9).
