# Benchmark methodology

The benchmark suite lives in [`bench/`](../bench/README.md). It measures actual
text or cell extraction from generated inputs; format detection, ZIP inspection and
PDF page counting without text extraction do not count as benchmark results.

## Inputs and provenance

[`bench/generate.mjs`](../bench/generate.mjs) creates the input files using the
repository's MIT-licensed source and its pinned `fflate` runtime dependency. Text
and values are synthetic and generated by deterministic code; no third-party
documents or text are included. The DOCX is exactly 5 MiB and contains 10,000
marked paragraphs. The XLSX contains 50,000 marked rows. The PDF contains 100
text pages with one unique page marker each. ZIP entries use a fixed timestamp.
To meet the 5 MiB DOCX size, deterministic filler characters are spread evenly
through its 10,000 paragraphs; the 60,000 marker characters identify paragraphs,
while the remaining text is size padding rather than representative prose. The
host details in each report describe the machine used for that run and do not
assert that it matches the PRD's “2023 laptop” target hardware. The committed
inputs and `bench/fixtures/manifest.json` include byte lengths and SHA-256 hashes.

## Process and measurements

The runner spawns a new Node process for each library, input and repetition. This
keeps parser heap state from carrying into the next sample. The default is three
repetitions with a 120-second wall-clock timeout per child and a 1024 MiB process
RSS ceiling. `BENCH_REPEATS` accepts 1–10, `BENCH_TIMEOUT_MS` accepts 1–600,000,
and `BENCH_MAX_RSS_MIB` accepts 1–8192. The parent caps combined child output at
1 MiB and kills the entire process group when it exceeds its time, output, or RSS
budget. On Linux it samples aggregate process-group RSS every 25 ms using `ps`;
each `ps` sample has a two-second timeout and a 1 MiB output cap, and an active
sample process is aborted when its benchmark child exits. Monitor failures and
unsupported platforms fail closed without timing results.

The worker reads the fixture and invokes the parser's public extraction API. It
builds text or cell output and verifies that every expected marker identity
occurs exactly once before marking the sample valid. An unsupported built-in reader is `UNAVAILABLE` and has
no elapsed time or memory number. An extraction that fails the full marker check
is `INVALID-OUTPUT`; its timing is excluded from the medians and PERF-1 pass/fail
decision.

Elapsed time covers the parser call through creation of semantic text/cell output;
identity validation happens after the timer. Reported peak RSS is the largest
sampled absolute RSS across the child process group, including Node runtime and
parser initialization. It is not a parser-only allocation measurement, and a
short spike between samples may be missed. The result page records Node version,
platform, architecture, CPU count, RAM, comparator versions, fixture sizes and
hashes. Compare runs only on the same machine and runtime setup.

Run from a clean build after creating or refreshing the inputs:

```sh
npm run build
node bench/generate.mjs
npm_config_cache=/tmp/bench-npm-cache npm install --prefix /tmp/docsluice-bench-deps --ignore-scripts --no-audit --no-fund --save-exact officeparser@8.1.1 mammoth@1.13.0 xlsx@0.18.5 pdf-parse@2.4.5 unpdf@1.8.1 pdfjs-dist@6.4.299
DOCSLUICE_BENCH_NODE_MODULES=/tmp/docsluice-bench-deps/node_modules node bench/run.mjs
```

The comparator packages are installed outside the repository, and install scripts
are disabled. The runner checks each installed package version against
[`bench/comparators.json`](../bench/comparators.json) and fails on a mismatch.
Missing packages are explicitly reported as unavailable and cause a nonzero exit.
The root `package.json` is outside this change's scope, so the canonical local
command here is `node bench/run.mjs`; the package owner can add
`"bench": "node bench/run.mjs"` to expose `npm run bench`.

## Verified comparison libraries

The exact versions below are pinned so package changes do not silently change the
comparison. Adapters use each library's public text or cell extraction API.

|---|---|---|---|

| `mammoth` | 1.13.0 / BSD-2-Clause | DOCX | `extractRawText({ buffer })`. [README/API](https://github.com/mwilliamson/mammoth.js), [npm metadata](https://www.npmjs.com/package/mammoth) |
| `xlsx` npm build | 0.18.5 / Apache-2.0 | XLSX | `XLSX.read(buffer)`, then `utils.sheet_to_json(sheet, { header: 1 })`. SheetJS documents that the npm package is stale and separately provides its current CDN build, so this row is explicitly the public npm distribution. [Node install guidance](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/), [parse options](https://docs.sheetjs.com/docs/api/parse-options/), [npm metadata](https://www.npmjs.com/package/xlsx) |
| `pdf-parse` | 2.4.5 / Apache-2.0 | PDF | `new PDFParse({ data }).getText()`. [README/API](https://github.com/mehmet-kozan/pdf-parse), [npm metadata](https://www.npmjs.com/package/pdf-parse) |
| `unpdf` | 1.8.1 / MIT | PDF | `getDocumentProxy(bytes)`, then `extractText(pdf, { mergePages: true })`; uses its bundled serverless PDF.js build. [README/API](https://github.com/unjs/unpdf), [npm metadata](https://www.npmjs.com/package/unpdf) |
| `pdfjs-dist` | 6.4.299 / Apache-2.0 | PDF | Direct PDF.js API: `getDocument({ data }).promise`, `getPage(n)`, and `getTextContent()`, using the legacy Node build. [Official examples](https://mozilla.github.io/pdf.js/examples/), [API reference](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [npm metadata](https://www.npmjs.com/package/pdfjs-dist) |

Two PRD section 21 descriptions need follow-up in the next PRD revision. Current
`officeparser` returns a structured AST rather than mostly plain text. The public
npm `xlsx` package is 0.18.5; it is distinct from SheetJS's newer official CDN
distribution. SheetJS's official Node installation page says npm is stale at
0.18.5, identifies 0.20.3 as the current CDN build, and says the cited prototype
pollution issue was fixed in 0.19.3 while the current Snyk finding is a tooling
false positive. Because this benchmark uses npm 0.18.5, that statement about
0.19.3 does not establish the security status of the benchmarked npm version. This
benchmark reports the npm version and does not generalize its result to the CDN
build or make an independent security claim. See the [official SheetJS Node
installation notes](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/).

## Current support gap

On the accepted base for this work, docsluice implements only the legacy DOC
reader. The benchmark's required DOCX, XLSX and PDF cases therefore report
`reader-not-implemented` for docsluice rather than measuring detection or archive
work as if it were extraction. PERF-1 remains unverified until the corresponding
readers are implemented (DOCX #29, XLSX #34, PDF #46). Comparator timings do not
establish docsluice performance or justify changing its limits.
