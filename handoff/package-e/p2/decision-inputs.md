# Package E P2 decision inputs (#86, #88)

Research note only (2026-10-09). This is not an ADR, implementation, dependency approval, or a claim that any reader exists. Issue text comes from the explicitly non-frozen `current-issues.json`; decisions still need the authoritative requirements archive and the blocked foundation. Repository clean-room policy (ADR 0003) requires implementations from public specifications/first principles; ADR 0011 allows runtime dependencies only with a new accepted ADR.

## #86 — RAR and 7z listing

**Recommendation (inference): plugin boundary, listing-only initial scope.** Keep both readers out of core. Once #41 supplies the registered plugin contract, a format plugin could expose bounded entry metadata and encrypted/unsupported status while relying on established ZIP/core budget and error contracts where applicable. No extraction, file-content reads, or codec dependency in this first slice. This respects the issue's plugin-candidate framing and the existing “few dependencies” policy; no new runtime package should be proposed without its own ADR.

RARLAB's current license explicitly says UnRAR source/binary may not be used or reverse engineered to recreate the proprietary RAR compression algorithm. That supports excluding decompression/recreation work from this proposal; it does not itself establish that every clean-room metadata parser is legally cleared. Implementing RAR listing should therefore use a public format specification and independent code, never UnRAR source, and receive a focused license review before adoption. The RAR format is versioned; define supported header generations and report unsupported/encrypted archives honestly. [RARLAB license](https://www.rarlab.com/license.htm)

7-Zip documents archive-header compression as a format feature and says LZMA is the default method; the LZMA SDK is public domain. **Caveat/inference:** an encoded/compressed 7z header must be decompressed before filenames, sizes, and entry metadata can be listed. A parser that only reads unencoded headers will miss common archives and must clearly return unsupported (never “empty”). Even if a clean-room LZMA decoder is legally possible, its memory/CPU limits and decoder maintenance need explicit evaluation; SDK license permissibility does not make its code copied into this repository automatically acceptable under ADR 0003. [7z format](https://www.7-zip.org/7z.html), [LZMA SDK license and capabilities](https://www.7-zip.org/sdk.html)

## #88 — VSDX, iWork, LaTeX

**Recommendation (inference): VSDX is the first low-cost value; defer iWork and treat LaTeX source as text with limits.** Microsoft specifies VSDX as a ZIP package with XML parts; page XML contains shapes and each shape may contain `<Text>`. A minimum golden fixture should be a legally sourced, tiny `.vsdx` with: two ordered pages (including an empty page); multiple shapes on one page; shape text with Unicode and line breaks; nested/grouped shape; text in a connector; a shape without text; and a deleted/hidden or unusual shape case to pin exclusions. Assert deterministic page/shape order, page labels/names, text preservation, no geometry-only noise, package relationship resolution, and safe behavior for malformed/missing relationships and hostile ZIP/XML limits. Capture a short golden rationale. **Inference:** v1 should emit readable shape text in page order and explicitly defer layout reconstruction, masters/style inheritance, embedded objects, formulas, and rendering. Reuse shared OOXML/ZIP helpers only after blockers #28 and #41 resolve. [MS-VSDX overview](https://learn.microsoft.com/en-us/openspecs/sharepoint_protocols/ms-vsdx/29bd5bbc-db66-46f9-906e-140c5a4e59c8), [MS-VSDX Page XML example](https://learn.microsoft.com/en-us/openspecs/sharepoint_protocols/ms-vsdx/dccbb4b5-ca0c-43ef-9379-00c1acb54377), [Microsoft VSDX introduction](https://learn.microsoft.com/en-us/office/client-developer/visio/introduction-to-the-visio-file-formatvsdx).

For iWork, Apple’s public developer documentation surfaced here covers exporting through its app API, not a stable IWA document-format specification. The issue's Protobuf/Snappy characterization is consistent with independent format-analysis references, but is not Apple-published normative material. This implies schema/version churn and substantial clean-room work; defer as plugin research, don't adopt a parser/dependency from an unofficial implementation without separate licensing and compatibility review. [Apple iWork Document Exporting API](https://developer.apple.com/documentation/iworkdocumentexportingapi). For LaTeX, keep the candidate narrowly as source text extraction, preserving source rather than stripping commands: macros/packages make reliable command stripping equivalent to partial TeX interpretation. The LaTeX Project publishes extensive command/kernel documentation, but it is not a simple source-to-prose mapping spec. [LaTeX Project documentation](https://www.latex-project.org/help/documentation/).
