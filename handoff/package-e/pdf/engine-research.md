# PDF engine research (documentation only)

**Date:** 2026-10-09. This is a candidate review for issue #44, not a runtime spike result or ADR decision. The frozen foundation archive could not be materialized, so its exact dependency pin is unknown. `unpdf@1.8.1` below is a research candidate only; no dependency change is authorized or proposed as complete.

Scaffold inputs consulted: `docsluice/docs/prd.md` (PDF-1..10, SEC-10/11, RT-1/5, PERF-1, QA-4), `docsluice/docs/adr/0009-pdf-engine.md` (Proposed), `docsluice/docs/adr/0011-dependency-policy.md` (Accepted allow-list), and issue snapshots #44–50/#82. The PRD targets Node 20+, Bun, Deno, browsers and edge workers; #44 also requires no eval/network/worker behavior, size and timing evidence. Issue #44 is blocked by #23, whose cross-runtime harness is unavailable in the supplied preparation context.

## Candidate and API

The tagged [unpdf v1.8.1 README](https://github.com/unjs/unpdf/blob/v1.8.1/README.md) documents `extractTextItems()` with page-indexed `x`, `y`, `width`, `height`, `fontSize`, `fontFamily`, `dir` and `hasEOL`, enough geometry for later reading-order (#46) and table (#82) work. It also exposes `getResolvedPDFJS()` for lower-level `getDocument(new Uint8Array(bytes)).promise`, `pdf.getPage(n)` and `page.getTextContent()` access.

The tagged [unpdf package.json](https://github.com/unjs/unpdf/blob/v1.8.1/package.json) gives exact package version `1.8.1`, but declares `engines.node >=22`—a direct conflict with docsluice's Node 20 support. It lists build-time `pdfjs-dist: ~6.1.200`. However, the same tagged README says the bundled PDF.js is `5.6.205`, and the [unjs.io package docs](https://unjs.io/packages/unpdf/) say `4.0.189`. The [release history](https://github.com/unjs/unpdf/releases) says v1.8.0 upgraded to PDF.js v6.1. These upstream version statements conflict. A harness must print `getResolvedPDFJS().version` from the exact installed tarball and record the lockfile/artifact before asserting the embedded engine version. Do not treat `1.8.1` as the foundation pin.

The [Mozilla PDF.js v6.4.299 release](https://github.com/mozilla/pdf.js/releases) is a comparison candidate for the legacy build. Its [API source](https://github.com/mozilla/pdf.js/blob/v6.4.299/src/display/api.js) describes text items with text, direction, transform, width, height, font name and line-break flag. It also creates a PDF worker when one is not passed, and can use a real Web Worker in browsers. Its Node path disables workers and uses a fake worker. `disableWorkerRendering` only governs page rendering; it does not disable document parsing workers. By contrast, unpdf says its serverless build inlines worker code and parses on the event loop without a worker. That is promising, but there is no documented `disableWorker` option: prove absence of workers at runtime.

## Candidate security configuration and caveats

For PDF.js initialization, test `data: Uint8Array`, `isEvalSupported: false` (if the selected version honors it), `useWorkerFetch: false`, `useWasm: false`, `disableAutoFetch: true`, and `disableStream: true`. Expose only binary `data`; reject URL, range, HTTP-header and base-URL inputs. PDF.js says disabling auto-fetch also requires disabling streaming. Worker fetch otherwise may fetch CMaps, standard fonts or WASM; any needed CMaps/font assets must resolve locally or be omitted with a bounded warning. Never configure remote URLs for `cMapUrl`, `standardFontDataUrl`, `wasmUrl` or document sources. Setting `useWasm: false` follows PDF.js's API, which documents WASM use as enabled by default.

There is a version caveat for eval: Mozilla's [security advisory GHSA-wgrm-67xf-hhpq](https://github.com/mozilla/pdf.js/security/advisories/GHSA-wgrm-67xf-hhpq) says affected versions can execute attacker-controlled JavaScript when `isEvalSupported` is true and gives `false` as a workaround; patched versions remove that eval path. The current v6.4.299 API reviewed does not document/read `isEvalSupported`, so determine whether the option is meaningful or ignored for each candidate. Regardless, static-scan the packed artifact and trap `eval`/`Function` in a CSP-like browser test. This is documentation evidence, not proof of inert behavior for this build.

Avoid `renderPageAsImage` and `extractImages`. The unpdf README says Node rendering needs optional native `@napi-rs/canvas`; its package metadata marks that peer optional. Do not add or import it. PDF.js `useWasm` defaults true, so set false for docsluice's no-WASM core requirement. unpdf also warns bare extraction methods process every page, raw `getDocument` does not apply its convenience safeguards, and its image-size default is unlimited. Check `numPages` before looping; enforce `pdfPages`, time, item and output budgets in docsluice and tick per page/batch. Use timeout/abort checks around event-loop parsing. Keep PDF actions as data; never dispatch JavaScript, Launch or remote GoTo targets.

## Proposed verification protocol

Run both candidates with exact lockfiles and report `getResolvedPDFJS().version`: unpdf `1.8.1` serverless build versus `pdfjs-dist` `6.4.299` legacy build. Use identical legal fixtures: single/multi-page text, CJK, malformed xref, and 100-page text. Test Node 20/22/24, Bun, Deno, headless browser and Workers simulator. For each: dynamic import only on PDF input; per-page positioned output; repeat determinism; network denied; worker constructors/threads trapped; no `eval`/`Function`; URL source rejected. Specifically report Node 20 separately because unpdf declares Node >=22. Record any unsupported runtime with a test-based reason; no runtime success is inferred from README claims.

Test action-bearing `/OpenAction`, `/AA`, `/Launch`, `/GoToR` PDFs with network spies and a JS side-effect sentinel. Check truncated/xref-damaged PDFs for bounded partial results or documented errors. Assert page/item/output limits stop promptly. Confirm missing CMaps do not cause a request. #44's current test harness blocker remains; these are proposed checks, not completed ones.

For size, build the actual deferred PDF subpath with production bundler flags; record exact bundler and source entry. Report raw/gzip bytes for the PDF entry and transitive chunks, core without PDF, and total consumer bundle with reachable dynamic import. This tests both RT-5's exception and whether lazy import keeps base size down. Use a fixed gzip tool/version, exclude source maps only if they are not shipped, and do not compare package-tarball size to built-bundle size.

For PERF-1, on a named 2023-class machine and Node 24, use identical 100-page input/config, one excluded warm-up and at least 10 measured runs per engine in alternating order. Report median, p95, min/max, input size, text/item counts and cold first-import/parse separately. Then verify the normal `timeMs` budget can stop an intentionally over-budget run. No measurements exist yet.

## Options and security evidence

The tagged unpdf `getDocumentProxy` type accepts PDF.js `DocumentInitParameters`; the official [PDF.js API reference](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html) documents `useWasm` (default true), `useWorkerFetch`, `disableAutoFetch`, and `disableStream`. Its v5.6.205 [tagged API source](https://raw.githubusercontent.com/mozilla/pdf.js/v5.6.205/src/display/api.js) defines `isEvalSupported` (default true in PDF.js itself), uses supplied document `data` without a PDF network stream, and uses `url`/range inputs to load network data. For the reader, pass only bytes; set `isEvalSupported:false`, `useWorkerFetch:false`, `useWasm:false`, and disallow remote asset URLs. `disableAutoFetch:true` should be paired with `disableStream:true` if any range/URL loading is ever permitted. No `disableWorker` parameter appears in v5.6.205 `api.js`; unpdf documents a serverless path with an inlined worker but says parsing runs on the event loop without a worker. Do not claim “worker disabled” from an option name; confirm actual thread/worker creation in the isolated A23 harness.

Security: Mozilla’s [GHSA-wgrm-67xf-hhpq](https://github.com/mozilla/pdf.js/security/advisories/GHSA-wgrm-67xf-hhpq) describes attacker-controlled JavaScript execution in affected PDF.js versions when `isEvalSupported` was true and gives `false` as a workaround. It lists affected versions through 4.1.392, patched at 4.2.67; the v5 candidate is beyond that affected range, but keeping eval disabled is prudent and must be tested on the selected bundle. The v1.7 README expressly documents the false default. The 1.8.1 README’s API-default paragraph omits that setting while its untrusted-PDF section says the defaults are safe against script execution; treat the effective 1.8.1 default as unknown until inspected/tested. unpdf documents `@napi-rs/canvas` as an optional peer required for Node rendering; do not load it for text extraction. PDF.js `useWasm:false` disables its optional WASM path; default is true.

**Conclusion:** No tag inspected declares a Node-20-compatible `engines` range. v1.7.0 is a concrete exact-version fallback for the blocked runtime experiment only, not evidence of compatibility. A manifest engine range is metadata, not proof of runtime support; conversely, missing `engines` is not proof of support. Preserve A23 as a blocker for runtime, worker/network/eval, dependency-closure, resource-budget, and size claims. No package was installed or run for this addendum.
