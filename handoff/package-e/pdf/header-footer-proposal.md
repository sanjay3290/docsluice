# Proposal: deterministic repeated PDF header/footer classification

**Scope:** Design input for issue [#48](https://github.com/sanjay3290/docsluice/issues/48) (PDF-3). This is a proposal for the later reader integration, not a code change, output golden, or claim of extraction accuracy. It assumes the private layout helper from #46 can provide ordered line text and page-relative geometry; the actual PDF text-item adapter/engine (#45) remains pending. Any helper/API shape below must be reconciled with those dependencies before implementation.

## Requirements and ownership

Issue #48 says to compare normalized line text (digits replaced with a placeholder) and normalized position in top/bottom page bands, and classify a candidate when it appears on at least 60% of pages and at least 3 pages. It authorizes `pdfHeaders: "remove" | "keep"`, defaulting to `"remove"`. Its golden expectations cover running headers, page-number footers, and alternating odd/even headers. PDF-3 in `docs/prd.md` describes repeated headers and footers as an option that defaults on. The issue is blocked by #46; the current E integration proposal also keeps the #48 reader connection gated on #45 and #27 runtime work. Public option wiring, registrations, and shared manifest changes remain integration-lead work. This document does not change those ownership boundaries.

## Candidate algorithm

1. **Collect all pages before emitting.** Obtain the #46 ordered lines plus page width, height, and rotation for every page. Convert each line's baseline/box to normalized page coordinates in `[0,1]`, using the rotated display page so top and bottom mean what a reader sees. Round geometry deterministically (the #46 proposal currently rounds to 0.001 units) before comparisons and sorting.
2. **Restrict candidates to bands.** A line can be a header candidate only if its normalized baseline center is in the top 10% (`y <= 0.10`); a footer candidate only if it is in the bottom 10% (`y >= 0.90`). These boundaries are a concrete initial proposal and should be tuned only with reviewed synthetic fixture evidence. Lines in the central 80% are never eligible, regardless of repeated wording.
3. **Normalize text narrowly.** Normalize Unicode to NFC, collapse runs of horizontal whitespace to one space, trim both ends, then replace each decimal digit run with `#` (so `Page 2 of 8` becomes `Page # of #`). Preserve case and punctuation to reduce accidental collisions. Ignore empty normalized strings. Do not use a broad fuzzy similarity rule.
4. **Match normalized positions.** Compare lines only within the same band and with the same normalized text. Treat normalized baseline centers as a match when vertical distance is at most `0.015` of page height and horizontal center distance at most `0.03` of page width; cluster candidates deterministically against a sorted representative/median position. This prevents equal text at unrelated body locations from joining one group. Fix and test the tolerances before integration rather than changing them opportunistically per fixture.
5. **Apply thresholds to distinct pages.** Count at most one occurrence of a candidate group per page. A group is repeated when it is on at least 3 distinct pages and on at least 60% of pages in its comparison set (`count / total >= 0.60`). Use integer comparison (`5 * count >= 3 * total`) to avoid floating-point boundary drift. For ordinary groups, the comparison set is all pages. Do not remove candidates in documents with fewer than 3 pages.
6. **Support alternating odd/even headers.** In addition to the all-page pass, group header candidates by one-based page parity. Apply the same ratio and minimum-three-page rule within each parity cohort. Thus each of two alternating signatures is eligible only when supported by at least 3 distinct odd/even pages and at least 60% of that parity cohort. This naturally means an alternating pair needs at least 6 pages to qualify both variants. Keep footer detection in the all-page cohort unless a fixture demonstrates parity-varying footers and the issue scope is updated.
7. **Avoid removing body text.** Only remove lines that satisfy both the position band and repeated-position/text threshold. A repeated phrase in the body remains. A single-page cover title remains. A line that merely shares a digit-normalized string with a header but is not at the same normalized position remains. Do not broaden a cluster across the boundary to capture nearby body lines.
8. **Emit stable output after classification.** First determine all groups, then emit output in original page order. In `remove` mode, remove every matched occurrence from page text and emit exactly one `header` or `footer` block per normalized-position/text group, using the earliest page as the representative location if location support exists. Order emitted header/footer blocks by band (header before footer), normalized position, then first-seen page and source order. Never emit a block during the scan pass. In `keep` mode, leave all lines in their page text and emit no extracted header/footer blocks.

This design is conservative: false negatives on short documents or slightly varying layout are preferable to suppressing body content. It does not infer semantic headers from font size or wording alone.

## Synthetic fixture plan and intended expectations

All PDFs should be generated from original synthetic content, carry CC0 provenance, and include a source-side geometry/text description. The listed positions and strings below are **intended fixture facts** from the generator. They are not claims that #45 extracts those strings or #46 reports those coordinates accurately. Once both dependencies exist, verify actual per-page extracted text and geometry before approving docsluice expected outputs.

| Fixture | Pages and intended text/positions | Expected classification from intended geometry |
|---|---|---|
| `running-header.pdf` | 8 pages; `Quarterly report` at top band, normalized center `(0.50, 0.055)` on all 8; distinct body paragraphs below `y=0.20`. | One header group at 8/8 pages. `remove`: body pages omit it and one header block is emitted. `keep`: each page retains it and no header block is emitted. |
| `numbered-footer.pdf` | 10 pages; `Page 1 of 10` through `Page 10 of 10` at bottom center `(0.50, 0.955)` on all 10. Include the page number in a separate page-label field only if PDF fixture construction supports it. | Digit normalization makes one footer group at 10/10 pages. `remove`: one footer block. `keep`: ten page-text occurrences, no footer block. PDF page labels are independent of footer detection. |
| `alternating-headers.pdf` | 8 pages; odd pages show `Northwind report` at `(0.22, 0.055)`; even pages show `Northwind report — confidential` at `(0.78, 0.055)`. Each signature appears on 4/4 pages of its parity cohort. | Two header groups from parity cohorts, each emitted once. Preserve each page's body. This checks parity handling and position grouping together. |
| `body-repetition-control.pdf` | 8 pages; `Important notice` occurs in body at `y=0.42` on every page; `Repeated heading` appears in the top band on only 2 pages; one unique title at top on page 1. | No header/footer candidates emitted: the body phrase is outside bands; the other phrases fail the 3-page minimum. All text stays in page text. |
| `threshold-boundaries.pdf` | 5 pages; a top-band candidate appears on 3 pages at a stable position, and another candidate on 2 pages. Use a second 3-page document for the exact 3/3 lower bound if needed. | 3/5 qualifies exactly at 60%; 2/5 does not. Include a 2-page document with identical top lines and assert no removal because minimum pages is 3. |
| `position-control.pdf` | 6 pages; same normalized phrase occurs at top on 3 pages and in the body on 3 pages, with distinct intended normalized y positions. | Only the top-position group qualifies; body occurrences are retained. No line is removed based on text match alone. |

For each fixture, record the page count, exact line text, baseline/box coordinates, rotation, and intended normalized coordinates in a sidecar description. The expected-output review should specifically check page count, retained page text, once-only block counts/order, location provenance, and byte-identical output across repeated runs/options.

## Integration tests and limits

- Unit-test normalization, band edges, position tolerances, threshold arithmetic, duplicate-on-one-page counting, parity cohorts, minimum-page behavior, stable sorting, and `keep` behavior against synthetic line/geometry records independent of the PDF engine.
- Once #45/#46 provide the real adapter and pipeline, add golden tests for the fixtures above. Verify actual extracted text and line geometry independently before converting intended fixture facts into output goldens.
- Verify that body text in the central 80% is never removed and that top/bottom repeated candidates below threshold remain in page text.
- Test rotated pages and geometry conversion once #46's coordinate convention is finalized. Do not guess orientation or coordinate semantics from the PDF generator alone.
- Public `ExtractOptions` ownership and host registration are lead-owned. This proposal only records the authorized `pdfHeaders` values/default and intended behavior.

The available PDF fixture preparation currently has no repeated-header/footer fixture and no docsluice output goldens for this behavior. Synthetic fixture generation can establish intended placement and wording, but actual PDF extraction accuracy, reader acceptance, cross-runtime behavior, and final threshold calibration remain unverified until #45/#46 integration and reviewed pipeline goldens.
